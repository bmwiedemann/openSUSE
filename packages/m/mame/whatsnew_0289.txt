-xerox/bigbord2: Boot CP/M, wire SASI HD, mark working (#15412) [David Rand]
 * xerox/bigbord2: Boot CP/M, wire SASI hard disk, fix warm-boot DRQ race
   - Brings the Big Board II driver from "MACHINE_NOT_WORKING" up to a functional state.  Five inter-related changes, all small and
      local to bigbord2.cpp.
   - 1) 74LS151 DMA-RDY mux: track the selected input dynamically. syslatch2 bits 0-2 select which of eight RDY sources feeds the
      Z80 DMA's /RDY pin; the existing driver only re-evaluated the mux inside syslatch2_w, so per-byte FDC DRQ / SIO WRDY edges
      that happen *after* a syslatch2 write never propagated to the DMA. Result: DMA boot read of the CP/M loader sets WD179x bit 2
      (Lost Data) and the BIOS prints "BIOS error on A: drq".  Fix: store m_dma_sel + an m_cc[8] cache of all eight mux inputs, then
      have fdc_drq_w / sio_wrdya_w / sio_wrdyb_w (and sasi_req_w below) call m_dma->rdy_w() whenever their index matches m_dma_sel.
   - 2) Soft-reset re-init.  The state above (m_dma_sel, m_cc[], DMA RDY level, m_fdc_rq, the NMI line) was left stale across a soft
      reset, so the boot DMA on the second cold-attempt session was non-deterministic.  machine_reset() now restores it to the
      power-on values the cold-boot ctors produce.
   - 3) FDC INTRQ + DRQ -> Z80 /NMI gate (HALT-conditional).  Per the schematic, the WD179x's INTRQ (pin 39) and DRQ are OR'd,
      inverted and AND'd with /HALT to drive /NMI -- so the CBIOS' HALT+INI PIO path moves one byte (or finishes a command) per NMI
      while the CPU is halted, but the gate stays quiet during a DMA transfer (CPU bus-released, not halted).  Implemented via the
      Z80 halt_cb() callback (zero polling latency) + a single m_fdc_rq byte tracking INTRQ in bit 0, DRQ in bit 1, and NMI-asserted
      in bit 7.  This is needed for CBIOS variants that use the HALT+INI path (e.g. cbios.s1) on warm boot's CCP reload; the V1.1
      monitor in bigbrdii.u85 is interrupt-driven and never halts, so the gate stays quiet for it.
   - 4) Race-window mask in fdc_status_r.  MAME's wd_fdc::command_end() clears BUSY without dropping DRQ when LOST_DATA is *not* set
      -- there's a literal "TBD: lost data should probably negate DRQ" comment in the code.  That exposes a transient BUSY=0 + DRQ=1
      state real WD179x DMA hardware doesn't (arbitration grabs the trailing byte before BUSY drops).  Without this mask the V1.1
      CBIOS' DISKOP polling exits its "wait for BUSY=0" loop, masks the returned status with AND $9F, sees bit 1 (DRQ) set, and
      reports "BIOS error on A: drq track N sector M" on every warm boot.  Re-assert BUSY in the status read while the race is open
      so the BIOS keeps polling; the DMA drains the data register within microseconds and the next read returns a clean STS=00. The
      byte stays in the FDC's data register -- the mask only delays when the BIOS sees the command complete, it doesn't fabricate or
      hide data.
   - 5) Xebec S1410 SASI hard disk subsystem.  Adds a small in-driver bigbord2_sasi_host_device that bridges between the BB-II's two
      SASI ports (D8 data / D9 status) and the nscsi bus + s1410 target.  D9 status bits map BSY=0x02, MSG=0x08, C/D=0x20, I/O=0x01
      and (for the DMA-variant ST412 BIOS) REQ=0x80.  SEL and RST come in through outlatch1 (U96, an LS259 addressable latch) Q3 and
      Q2.  SASI REQ is surfaced via req_cb() so it can feed mux input 7 to the DMA RDY; the cbios.s2 INIR variant uses the DMA's
      read-status command to wait for REQ, the DMA-variant reads D9 bit 7 directly.  An optional set_seek_timing() call from
      machine_start() opts the s1410 into a realistic ST-506 cylinder-aware seek model (3 ms track-to-track, 85 ms average, 205 ms
      full-stroke at 3600 RPM, 1:1 interleave -- per the April 1982 ST412 OEM manual) -- depends on the s1410 changes submitted as a
      separate PR.
   - PAL ROM declarations for U23 (PAL16L8) and U34 (PAL10L8) are added as NO_DUMP -- the parts have their security fuse blown, but
      the mem/io decode is already hard-coded from the CUPL equations in the existing roms/bigbord2/BB2_U23_Replacement.txt and U34
      counterpart, so the ROMs are cosmetic for the audit.

-bus/nscsi/s1410: Add an optional cylinder-aware seek-timing model (#15411) [David Rand]
 * Mirrors the dtc510 approach: introduces an opt-in set_seek_timing(track_us, average_us, full_us, rpm, interleave) API that
    replaces the device's legacy flat 85 ms per-command delay with a power-law model fitted to the published track-to-track,
    average, and full-stroke seek times.  No call from a driver -> behavior is unchanged for the existing s1410 users (victor9k,
    mikromik, x37_sasi, db4105, idpartner_sasi).
 * The model state lives on the device:
   - m_seek_model: enable flag (false until set_seek_timing() is called)
   - m_last_cylinder: head position so subsequent same-cylinder I/O is billed at rotational latency only, not a fresh average seek
   - m_interleave / m_rpm / m_seek_track_us / m_seek_range_us / m_seek_exp: the fitted curve parameters
     * scsi_data_command_delay() then:
   - Same-cylinder I/O (dist == 0): rev_us * interleave / spt
   - Cylinder change: rev_us/2 (avg rotational latency) + track_us + range_us * (dist / ncyl)^exp
     * The exponent is solved from the three calibration points so an average-length seek (~1/3 stroke) costs exactly average_us.
        For the ST-506/ST-412 (track 3 ms, average 85 ms, full-stroke 205 ms per the April 1982 ST412 OEM manual) that gives exp ~=
        0.82, which captures the controller's "burst mode" multi-cylinder behavior -- faster than naive 3 ms/cyl stepping for long
        seeks while still cheap on short ones.
     * The header documents the API with ST-506 and ST-412 invocations side by side.  Both drives use identical set_seek_timing()
        parameters because the controller's burst mode adapts to the CHD's reported cylinder count via image->get_info().cylinders
        -- the 5 MB ST-506 (153 cyl) and the 10 MB ST-412 (306 cyl) are distinguished only by the physical media size, not by the
        timing call.

    controller built on it without subclassing.
 * set_seek_timing(), the model state, the fitted-exponent math (seek_time()) and a generic scsi_data_command_delay() now live in

-bus/scsi/scsihle: deassert REQ between phases; hold BSY in COMMAND (#15453) [David Rand]

    lines settled. Previously the per-byte REQ-deassert timer was cancelled by the next phase's re-assert, leaving REQ continuously
    high across e.g. COMMAND->DATA-IN, so an initiator that samples the control lines on the REQ edge read the stale previous-phase
    C/D/I/O.

    the connection.

-formats/imd_dsk: Add save support (IMD write for flopconvert) (#15385) [David Rand]
 * formats/imd_dsk: Add save support
   - IMD has been read-only in MAME's flopimg pipeline since 2017 — load() parses ImageDisk files, but flux-level images (MFI,
      captured floppies, running emulation state) cannot round-trip back to IMD.  This change implements imd_format::save() so
      flopconvert and any future driver-side "save as IMD" path work in both directions for standard MFM and FM media.
   - The save side decodes the flopimg flux representation per track, detects MFM vs FM and cell-size by scoring four common
      (encoding, cell_size) combinations (MFM @ 1000/2000 ns and FM @ 2000/4000 ns covering 250 and 500 kbps in both modes), then
      emits Dunfield IMD 1.20 records.  Per-track detection handles mixed-density disks (e.g. CP/M boot disks with an FM 128-byte
      boot track on cyl 0 head 0 and MFM data tracks elsewhere) automatically.
   - Specifics:
     * New imd_format::extract_track_rich() walks the MFM/FM bitstream once and produces records carrying physical sector order,
        DAM-deleted flag, and CRC validity for both address and data records.  The shared extract_sectors_from_bitstream_*_pc()
        helpers in flopimg.cpp discard this information; rather than widen them and disturb every caller, this format keeps a local
        extractor.  Flux-noise phantom IDAMs are filtered by requiring addr_crc_ok or data_crc_ok at the push site and by
        deduplicating shared sector IDs to prefer the candidate with the best CRC status.
     * New imd_format::detect_track() probes the four (encoding, cell_size) combinations per track and picks the one with the most
        cleanly- decoded sectors, scored by IDAM CRC.  Re-runs per track so mixed- density disks decode honestly without per-driver
        tuning.
     * New imd_format::save() walks tracks in IMD's canonical order, emits per-track records with the right mode byte, sector
        numbering map, optional cyl/head maps, and per-sector type byte (with the compressed-fill optimisation for sectors whose
        bytes are all the same value).  Deleted DAM and bad-CRC sectors round-trip to IMD types 3-8 as appropriate.
     * Header timestamp + comment are preserved across an IMD->IMD pass via a mutable string member captured on load(); other source
        formats produce a fresh "IMD 1.20: <localtime>" header with a short "Created by MAME flopconvert" annotation.
   - Validation:
     * 24 / 24 disks in a local archive of T-200 5.25" DSDD images (mixed-density boot tracks; bad-CRC sectors; rescue-merged tracks
        combined from multiple Greaseweazle captures) round-trip byte-identical at the sector-data level (header timestamps differ
        as expected).
     * Cross-validated against a Greaseweazle-produced IMD of an 8" T-250 bios.001-1.imd disk: byte-identical sectors after IMD ->
        MFI -> IMD.
   - Limitations (warn / refuse rather than corrupt):
     * Refuses to save tracks with mixed sector sizes within a single track — IMD has no way to represent that.
     * Probes the four common (encoding, cell_size) pairs; tracks at 300 kbps (IMD modes 1 / 4) fall back to mode 5 (MFM 250).
        Adequate for all CP/M and PC media; rare exotic disks would need the probe list extended.
 * formats/imd_dsk: Drop mutable comment cache; always emit fresh header
   - Per review feedback on PR #15385: the format manager is a const singleton, so caching per-image state on it via `mutable` is
      wrong (it would race under concurrent loads).  Remove `m_loaded_comment` and the two read sites (clear in load() entry, assign
      at load() exit, preferred branch in save()).
   - save() now always emits the generic "IMD 1.20: <localtime>" / "Created by MAME flopconvert" header — IMD->IMD passthrough no
      longer carries the source disk's first-line text forward.  Header is purely informational; data-emission path is unchanged,
      and round-trip byte fidelity at the sector level is unaffected.
 * formats/imd_dsk: Use std::localtime for portability
   - CI Windows builds (clang-x64, clang-arm64, gcc-x64) failed because localtime_r is POSIX-only.  Switch to dereferencing
      std::localtime's thread-local result, matching the existing pattern in src/lib/util/timeconv.cpp (which uses *std::gmtime in
      the same way). Portable across Linux, macOS, and Windows.
   - Single call from a single-shot save() routine, so the thread-local buffer's reuse hazard does not apply here.
 * formats/imd_dsk: Fix 8" media handling on load and save
   - Two related fixes for 8" floppy disks that surface together because both stem from load() not propagating media metadata:
   - 1) detect_track() probed only 300 RPM cell rates (1000/2000/2000/4000 ns).  MAME's internal flux representation is canonical
      200,000,000 ns/revolution regardless of disk RPM, so 360 RPM media stores its cells at different internal cell_sizes than 300
      RPM media:
   - 300 RPM, MFM 500 kbps: 1000 ns/cell  (5.25" HD, 3.5" HD) 360 RPM, MFM 500 kbps: 1200 ns/cell  (8" DSDD/SSDD) ...
   - The 20% cell-size mismatch overruns the PLL's ~25% lock tolerance for MFM density, so 8" disks loaded through any FF_8 driver
      and saved back to IMD lose every MFM track -- detect_track returns "mode 3 with no sectors" and save emits empty 5-byte stubs.
      Adds the four missing 360 RPM probes alongside the existing 300 RPM ones.  5.25"/3.5" media at 300 RPM is unaffected: the new
      probes simply score zero on it and lose the per-track contest.
   - 2) load() did not call image.set_form_variant() on the loaded image. The floppy_image therefore kept FF_UNKNOWN/variant=0,
      which propagates to any subsequent save (the MFI header records form_factor=0 instead of "8   "/"SSDD") and to MAME runtime
      code that consults image.get_form_factor() for rotation rate / cell timing.  Adds inference from track count + density +
      heads:
     * 77-track  -> FF_8 + SSDD/DSDD/SSSD/DSSD by encoding + sides
     * 40-track  -> FF_525 with the same per-encoding/per-sides logic
     * 80+ track -> FF_525 (ambiguous 5.25"/3.5"; 525 is the IMD-era default and the 500/250 kbps probe selection handles either)
   - When the caller supplied a real form_factor, it is preserved and only the variant is inferred.
   - Validation: a 77-track 8" SSDD CP/M boot disk (Big Board II DDBOOT.S1.imd) with an FM 128-byte boot track 0 plus 76 MFM
      1024-byte data tracks round-trips byte-identical at the sector level through imd -> mfi -> imd, and now also round-trips
      through a real MAME session (mount writable, write a file from CP/M, exit) without losing the MFM tracks.

-cpu/ns32000: account for bus width in operand access timing (#15493) [David Rand]
 * top() charged 16-bit-bus operand timings on every device variant: an aligned 32-bit operand cost two bus cycles on an NS32032,
    double the correct figure, making 32-bit-bus parts uniformly slow.  Generalize to the device's bus width: the first bus cycle
    costs 3 (4 with address translation), each additional one 4, with the cycle count derived from operand size, alignment and bus
    width.  The 16-bit case reproduces the previous values exactly; the NS32008 is now correctly charged 8-bit-bus timings.
 * Calibrated against period hardware: dhrystone 1.1 compiled with the 1985 Green Hills/Definicon toolchain, run on an emulated
    DSI-32 coprocessor (NS32032-10), scores 1290-1360 dhrystones/second against the official result of 1282-1315 for the real board
    (previously 970-1100).

-machine/nscsi_hle: allow targets to defer phase transitions (#15483) [David Rand]
 * An nscsi_full_device target previously had to queue its entire phase sequence (data, status, message) before returning from
    scsi_command(), so a command involving slow media work had to complete synchronously.
 * Make TARGET_NEXT_CONTROL hold the connection in the current state when the control queue is empty instead of popping an invalid
    entry, and resume stepping when scsi_data_in()/scsi_data_out()/ scsi_status_complete() push new entries.  A target can now
    return from scsi_command() with nothing queued, run the medium operation off a timer, and queue the data/status phases when it
    finishes.
 * Targets that queue everything up front never reach the new path; no behavior change for existing devices.

-machine/ns32082: fix translated address composition, do not translate interrupt cycles (#15499) [David Rand]

-machine/ns32202: track level-triggered pending state, honor in-service priority on acknowledge (#15500) [David Rand]
 * Level-triggered pending bits now continuously reflect the input lines: a bit clears when its line is no longer active, including
    when ELTG or TPL writes change a bit's effective sense.  Software uses this to dismiss and re-arm latched interrupts by toggling
    a line between level and edge sensing.
 * In fixed-priority (NTAR) mode, interrupt acknowledge no longer acknowledges a pending interrupt that an in-service interrupt of
    higher or equal priority blocks (an equal-priority in-service cascade remains acknowledgeable); a blocked acknowledge returns
    the spurious vector, as the hardware would never have asserted INT for it.  The interrupt output is fully re-evaluated after

-machine/ncr5385: complete selection as soon as the target responds (#15513) [David Rand]
 * scsi_ctrl_changed() only advanced the state machine on a target BSY when SEL was no longer asserted, which is the post-selection

-es5510.{h,cpp}: When writing data to DOL, round towards zero. (#15527) [Christian Brunschen]
 * A bug report by sjs@sojusrecords.com identified residual noise when playing certain sounds on an SD-1 - specifically, the
    OMNIVERSE sound has a reverberating tail that goes to silence on a real SD-1, but retains a never-ending tail on an emulated
    SD-1.
 * They investigated this further and found that this was consistent with a different, undocumented rounding difference when writing
    data to DRAM: whereas the documentation suggests a simple truncation of the internal 24-bit value to 16 bits, which is in effect
    rounding towards negative infinity, changing this to rounding towards zero eliminates the residual noise.
 * This change is based in part on the patch they sent me.
 * Further, per the es5510 documentation,
 * > ## 3.5.3 RAM Data Interface > > # Data Input Latch (DIL) > > [...] The DIL is 16 bits wide, left justified, so programs
    accessing > the DIL will see the least significant 8 bits as 0. > > [...] > > # Data Output Latch (DOL) and FIFO > > [...] Like
    the DIL, it is also 16 bits wide and is left justified.
 * Accordingly, change the type of `dil` to `uint16_t` and `dol` to `uint16_[2]`; and move the shifting and rounding aspects to when
    the emulation reads/writes DIL and DOL internally, rather than when they values are read or written to/from RAM / IO. This seems
    like it would be closer to how the chip probably works internally.

 * Three fixes for ncr5380-family controllers driven as CPU pseudo-DMA initiators, found during pc532 (DP8490) bring-up:
   - state_step(): a DMA wait state polling for a REQ/phase change returned no delay, so state_timer() re-armed at zero, freezing

-imagedev/floppy: derive twosid_r() from media variant (#15418) [David Rand]
 * imagedev/floppy: derive twosid_r() from media variant
   - Read media-sided-ness from the floppy_image variant tag rather than from observed track data via get_actual_geometry().  Drives
      sense single- vs double-sided media physically (e.g. 8" Shugart TS# on pin 30, from the index-hole position) so the answer
      must come from the media itself, not from whether the host happens to have written to head 1.  An unformatted SSSD diskette is
      still single-sided.
   - Before this change, twosid_r() reported TWO-SIDED to a host BIOS for any freshly-mounted unformatted media (heads==0 from
      get_actual_geometry returns false) and could permanently mis-report after a host wrote spurious noise to head 1 of a
      single-sided diskette.
   - No call-site changes needed: all 17 twosid_r() callers and the uPD765 ST3 plumbing already do the right thing once this returns
      correctly.
 * imagedev/floppy: fall back to geometry when variant is untagged
   - twosid_r() switched on the variant tag with default=two-sided, which relied on every format setting the variant.  Formats that
      never call set_variant() leave it 0 and were silently reported two-sided.  Treat variant 0 as 'unknown' and fall back to the
      previous get_actual_geometry() result, so untagged formats keep their old behaviour while tagged media get the deterministic
      answer.

-mc68681: fix transmitter deadlock in tra_complete (#15564) [David Rand]
 * The transmit-complete handler chose the next transmitter state from the TxRDY status bit rather than from whether another byte
    was queued in the THR.  On a race between a CPU THR write and the final bit-time of the byte being shifted out, two cases could
    permanently wedge the transmitter:
   - completion with TxRDY set and a byte buffered took the "else" path, set TxEMT, and dropped the buffered byte;
   - completion with TxRDY clear and nothing buffered did nothing, leaving the transmitter idle with both TxRDY and TxEMT clear.
     * In either case TxRDY never re-asserts and the transmit clock stays stopped, so a byte never drains and a polled transmitter
        spins forever waiting on TxRDY.
     * Decide from the queue instead: load a buffered byte if one is present, otherwise mark the transmitter idle by setting both
        TxRDY (THR empty) and TxEMT (shift register empty).  This is a no-op on the normal path, where tra_callback has already set
        TxRDY by the time completion is reached.

-sega/model1: HUD layering, blink palette and wireframe fixes (#15597) [Francisco José García García]
 * sega/model1: tile palette bit15 = intensity/shade bit
   - The Model 1 tile palette top bit (bit15) is an intensity/shade bit, not an unused 'x' as the plain xBGR_555 decode assumes.
      Almost every entry has it set (full brightness); a handful clear it to render dimmed - e.g. the Star Wars Arcade menu backdrop
      pen (palette[0]=0x7777).  Ignoring the bit left those pens too bright (the FIGHTER CONTROL backdrop rendered bright blue
      instead of the arcade's grey).
   - Replace the COL region's plain palette_device::write16 with a handler that halves the channels when bit15 is clear.  0x7777 ->
      (94,111,119), matching the arcade; entries with bit15 set are unchanged.
 * sega/model1: moiré direct poly on transparent pen fades to backdrop
   - A Star Wars Arcade gunner 2nd-viewport overlay is a single moiré (stipple-translucent) direct poly whose flat colour resolves
      to the transparent texture pen (index 0x1000 -> palette 0x8000 -> black).  Painting the pen literally gives a hard black/scene
      checkerboard over the gunner; the arcade alternates backdrop/scene.
   - Treat a moiré direct poly on the transparent pen as a "fade toward backdrop" overlay and paint the backdrop pen (0x400) so the
      stipple reads backdrop/scene/backdrop/scene.  Scoped to push_direct (2D direct polys) so 3D object shadows are untouched.
 * sega/model1: draw direct polys above the HUD tilemaps
   - The Star Wars Arcade FIGHTER CONTROL / cockpit screens put their callouts, pointer lines and viewport tints in direct
      (2D-projected) polys, which the hardware draws on top of the tilemap HUD.  They were rendered interleaved with the 3D objects,
      so the indicators ended up buried under the HUD.
   - Split tgp_render into two passes selected by render_pass: the first walks the display list drawing only the 3D objects
      (skipping the direct blocks), then the HUD tilemaps are composited, then a second pass walks the list again and draws only the
      direct polys, on top of everything.  Display-list state (matrices, viewports, lighting, RAM uploads) is re-applied identically
      in both passes so the direct polys project with the correct viewport.
   - push_direct previously guarded its vertex projection on z > 0 and snapped behind-"camera" vertices to (0,0).
      project_point_direct only offsets x/y by the viewport centre and ignores z, so that guard spawned huge spurious triangles
      radiating from the screen origin - harmless while buried under the HUD, but a bogus red cross over the SWA cockpit once the
      direct polys draw on top.  Project every direct vertex unconditionally instead.
 * sega/model1: tile colour mode field (blink, unlit UI elements)
   - Bits [11:10] of the tile colour word select a colour mode.  Bit 10 marks a flat UI element (radar blips, HUD text) that is
      drawn unlit at full intensity instead of being shaded by the scene lighting; mode 01 additionally blinks, rotating the BGR
      channels on alternate frames (the radar blips).
 * sega/model1: rasterize degenerate quads as wireframe lines
   - Line primitives reach the rasterizer as a quad with two coincident vertex pairs. Drawing them with the scanline filler
      collapses near-horizontal wires to a few pixels, so detect that case and draw a proper line instead (e.g. the Star Wars Arcade
      target box).
 * sega/model1: draw 0x41 objects above the HUD with a stencil
   - Reorganise rendering into a below-HUD pass (0x01 objects and 0x02 direct polys, sharing the per-viewport z-sort) and an
      above-HUD pass for the 0x41 objects such as the Star Wars Arcade radar blips. The hardware only lets the above-HUD objects
      show through "background" HUD pixels, so the HUD is snapshotted before the pass and its bright features restored over the
      result.
 * sega/model1: invert moiré checkerboard parity
   - Draw the moiré dither on the opposite pixels in both the scanline filler and the wireframe line, matching the hardware pattern.
 * sega/model1: iterate overlay stencil by scanline within cliprect
   - Walk the snapshot/restore buffers with row pointers over the cliprect instead of a flat loop with a divide and modulo per
      pixel, and name the near-black threshold.

-mc68681: assert TxRDY at the THR->shift transfer (#15613) [David Rand]
 * GitHub PR #15564 cured a transmitter deadlock but asserted TxRDY (together with TxEMT) only in tra_complete's idle branch, i.e.
    at end-of-transmission. Per the SCN2681/MC68681 datasheet TxRDY is asserted at the THR->shift-register transfer, one full
    character time earlier, so firmware that pipelines on TxRDY (the Ensoniq VFX inter-board link and MIDI, e.g. sd132) saw the
    ready window a character time late and dropped bytes, tripping SYSTEM ERROR 144.
 * Assert TxRDY in the reload branch where the queued THR byte transfers into the shift register; the idle branch sets TxEMT only.
    This keeps #15564's deadlock cure (TxRDY still re-asserts whenever a byte is queued) while restoring the correct one-character
    buffering window.
 * Tested on sd132 (VFX) and pc532 System V (4x SCN2681 console).

     * DMA phase mismatch and DRQ (6.7, 10.3, 10.5.2): a send leaves the request for the next, never-transferred byte pending across
        the mismatch ("the DRQ signal does not reset when a phase mismatch interrupt occurs"); the host completes the transfer by
        cycling DACK once more so ACK can release.  A receive has no pending request, so raising DRQ there fed pseudo-DMA read loops

        register paths.

-sega/model1: Clip wireframe lines to the viewport (#15712) [Francisco José García García]
 * The wireframe rasterizer walked its Bresenham from raw projected coordinates. Those come from the unclipped projection, and a
    degenerate projection (z ~ 0 with the boot-time zoom still 0) yields inf/NaN, whose float->int conversion is undefined
    behaviour: x86 hosts get INT32_MIN where arm64 saturates and maps NaN to 0. wingwar generates such vertices while booting, and
    on x86 the resulting (INT32_MIN, INT32_MIN) pairs matched the two-distinct-vertices wireframe case and walked a ~2^31-pixel line
    with overflowing error terms - the gray screen boot lockup reported against GitHub PR #15597 (Windows only, and only when the
    below-HUD pass draws, since the above-HUD pass pushes no geometry there).
 * Before that rasterizer existed these quads went through the scanline filler, which fill_slope()/fill_line() clamp to the
    viewport, so the same garbage stayed harmless and bounded. Give the line rasterizer the same property: Liang-Barsky clip the
    segment to the viewport before walking it. In-view lines are untouched; wires that used to leak a few pixels past the viewport
    edge now stop at it like every other primitive. Attract snapshots of vf, vr, vformula, swa, wingwar and netmerc are
    pixel-identical to master apart from one such leak. Verified against the boot hang by mimicking x86 conversion semantics on
    arm64: hangs before, completes after.

-video/zeus2: Fix Cruis'n Exotica road rendering (#15719) [JvM]

   - The "Fast HSR Removal" pre-cull tested only the view-space Z of the polygon normal, an orthographic facing test applied before

      camera, resulting in portions of the Cruis'n Exotica road being missing.
 * video/zeus2.cpp: Add near-plane clipping and perspective-correct texturing. [mourix]
   - Quads straddling the near plane were rejected outright, which dropped the nearest road segment in Cruis'n Exotica. Clip them

   - Textures were U/V interpolated linearly in screen space, which warped the geometry straddling the screen edge. Now carry U/Z,
